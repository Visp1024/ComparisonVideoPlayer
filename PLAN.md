# ComparisonVideoPlayer — план проекта

Видеоплеер для Windows для покадрового сравнения видео: точный пошаговый просмотр,
синхронное воспроизведение двух роликов и редактируемый таймлайн в стиле видеоредактора.

## 1. Требования (из постановки)

- Windows-приложение.
- Покадровое воспроизведение: шаг вперёд/назад ровно на один кадр, точный seek.
- Если прямой покадровый доступ невозможен/медленный — при открытии строим кэш кадров через ffmpeg.
- Два видео воспроизводятся параллельно и синхронно.
- Вместо стандартной полосы прокрутки — модифицируемый таймлайн (как в видеоредакторах):
  - настройка воспроизводимого отрезка (in/out точки);
  - сопоставление (выравнивание по времени) видео из параллельных треков.

## 2. Исследование технологий

| Вариант | Плюсы | Минусы |
|---|---|---|
| **.NET 8 + WPF + FlyleafLib (FFmpeg/D3D11)** — рекомендуется | C# (знакомый стек); FFmpeg = поддержка всех кодеков; встроенный frame stepping (`ShowFrameNext`/`ShowFramePrev`); аппаратный декод и D3D11-рендер; несколько независимых `Player`; активно поддерживается (3.10.x, FFmpeg v7/v8, WPF/WinUI3) | Таймлайн придётся писать самим (WPF Canvas); шаг назад на long-GOP зависит от реализации библиотеки — требует проверки |
| libmpv, встроенный в WPF/Qt | Лучший в классе playback; `frame-step`/`frame-back-step` из коробки | Интеграция через C API/HWND; синхронизировать два инстанса сложнее; UI всё равно свой |
| Electron + WebCodecs | Самый дешёвый в разработке UI таймлайна (HTML/CSS); покадровый декод под полным контролем | Демуксинг свой (mp4box.js и т.п.); ограничения кодеков (HEVC); два параллельных 4K-декода тяжелы; память/упаковка |
| Python + PyAV + PySide6 | Быстрый прототип | Производительность, упаковка, долгосрочная поддержка хуже |

**Решение (по итогам фаз 0 и 0б): .NET + WPF + FlyleafLib.** Один язык для логики и UI,
полный контроль над кадрами через FFmpeg, готовый плеерный движок.

Запасной вариант libmpv **проверен и отклонён**: спайк ([docs/spike-libmpv.md](docs/spike-libmpv.md))
показал, что шаг назад у него не быстрее, а на 5–8 % медленнее — 85 / 1194 / 494 мс против
68 / 1112 / 469 мс у FlyleafLib на H.264 GOP 25, H.264 GOP 250 и HEVC GOP 250. Узкое место —
декод long-GOP, а не библиотека; интеграция libmpv при этом дороже (HWND-хостинг и C API
вместо WPF-контрола). Точность seek у обеих библиотек покадровая.

**Целевой TFM — .NET 9** (а не 8, как выше в таблице): на машине разработки нет SDK 8,
FlyleafLib 3.10.4 (`net8.0-windows`) подключается к .NET 9 без проблем.

## 3. Архитектура

```
+--------------------------------------------------------------+
| WPF UI                                                       |
|  +----------------+  +----------------+                      |
|  | VideoView A    |  | VideoView B    |   (layout: рядом /   |
|  +----------------+  +----------------+    один/два трека)   |
|  +------------------------------------------------------+    |
|  | TimelineControl: линейка, 2 трека, клипы с trim,      |    |
|  | playhead, зум, снэп по кадрам, offset перетаскиванием |    |
|  +------------------------------------------------------+    |
+--------------------------------------------------------------+
| SyncEngine: мастер-клок, транспорт (play/pause/step/speed),  |
| маппинг время-мастера -> локальное время каждого трека       |
+--------------------------------------------------------------+
| PlaybackBackend (интерфейс)                                  |
|   +-- FlyleafBackend: прямой декод, frame step, точный seek  |
|   +-- FrameCacheBackend: кадры из кэша ffmpeg (fallback)     |
+--------------------------------------------------------------+
| CacheBuilder (ffmpeg CLI): фоновая генерация кэша/миниатюр   |
+--------------------------------------------------------------+
```

Ключевые модели: `MediaInfo` (fps, длительность, число кадров, VFR-флаг),
`ClipSegment` (источник, in/out, offset на треке), `SessionProject` (сохранение сессии в JSON).

## 4. Ключевые технические решения

### 4.1 Покадровое воспроизведение — три уровня

1. **Прямой шаг декодером** (основной путь): `ShowFrameNext`/`ShowFramePrev` у Flyleaf.
   Вперёд — тривиально; назад на long-GOP кодеках требует декода от предыдущего
   keyframe — скорость зависит от длины GOP.
2. **RAM-кэш вокруг playhead**: кольцевой буфер уже декодированных кадров
   (например ±N кадров), чтобы шаг назад был мгновенным в рабочей зоне.
3. **Дисковый кэш через ffmpeg (fallback из постановки)**: если формат «тяжёлый»
   (длинный GOP, HEVC/AV1, медленный шаг назад), при открытии в фоне строим
   all-intra прокси (`-g 1`, H.264 или MJPEG) либо извлекаем кадры; после этого любой
   seek/шаг мгновенный. Показ прогресса, кэш переиспользуется между запусками
   (ключ — хэш файла + параметры).

Решение о fallback принимается автоматически по замеру времени шага назад, с ручным
переключением в настройках. **Реализовано в фазе 4**: замер один раз на файл (порог 250 мс),
режимы «авто / всегда / никогда», настраиваемая частота прокси (кадров в секунду),
лимит хранилища с LRU-очисткой.

### 4.2 Синхронизация двух видео

- Единый **мастер-клок** в SyncEngine; оба плеера — ведомые: транспортные команды
  (play/pause/step/seek/скорость) идут через движок, никогда напрямую в плеер.
- Позиция трека = `master_time - track_offset`, обрезанная по in/out клипа.
- Разные fps у треков: шаг задаётся кадрами мастер-трека (выбираемого), ведомый
  сопоставляется по времени (ближайший кадр).
- Контроль рассинхрона: при воспроизведении периодическая коррекция ведомого,
  при паузе/шаге — точный seek обоих.

### 4.3 Таймлайн (кастомный WPF-контрол)

- Линейка времени с зумом (колесо) и панорамированием, снэп к границам кадров.
- 2 трека; на каждом клип с ручками trim (in/out — воспроизводимый отрезок).
- Перетаскивание клипа по треку = offset (сопоставление видео между треками).
- Playhead с прокруткой (scrub) — покадровая точность.
- Опционально: полоска миниатюр на клипе (ffmpeg-генерация в фоне), маркеры.

## 5. Этапы работ

- **Фаза 0 — спайк (валидация стека). Сделана**, см. [docs/spike-flyleaf.md](docs/spike-flyleaf.md):
  критерий «шаг назад ≤ ~200 мс» на 4K long-GOP не выполнен (1,1 с H.264 / 0,47 с HEVC),
  seek покадрово точен, два плеера работают без взаимного влияния.
- **Фаза 0б — спайк libmpv (запасной бэкенд). Сделана**, см. [docs/spike-libmpv.md](docs/spike-libmpv.md):
  libmpv не быстрее на шаге назад, бэкенд остаётся FlyleafLib. Следствие для плана:
  фаза 4 (кэш кадров) и RAM-кэш вокруг playhead — обязательный, а не опциональный механизм.
- **Фаза 1 — MVP одиночного плеера. Сделана**, см. [docs/phase1-mvp.md](docs/phase1-mvp.md):
  приложение `src/ComparisonPlayer` — открытие файла (диалог, drag&drop, аргумент командной
  строки), play/pause, шаг ±1 и ±10 кадров, таймкод и номер кадра поверх кадра и в транспорте,
  шкала позиции, панель сведений (fps, длительность, число кадров, VFR-флаг). Интерфейс
  `PlaybackBackend` и реализация `FlyleafBackend` разделены — фаза 4 подставит кэш кадров,
  не трогая UI.
- **Фаза 2 — таймлайн. Сделана**, см. [docs/phase2-timeline.md](docs/phase2-timeline.md):
  `Timeline/TimelineControl` вместо шкалы позиции — линейка с зумом колесом к точке под
  курсором и панорамированием, снэп, playhead покадровой точности, отрезок воспроизведения
  ручками на клипе и клавишами `I`/`O`, петля по отрезку, скорость воспроизведения.
  Миниатюры и полоса готовности кэша фазы 4 переехали на клип.
- **Фаза 3 — второй трек и синхронизация. Сделана**, см. [docs/phase3-sync.md](docs/phase3-sync.md):
  `Tracks/SyncEngine` (мастер-клок, транспорт только через движок, позиция трека
  `master_time − offset`), `Tracks/PlayerTrack` (движок, сдвиг, отрезок и кэш на трек),
  таймлайн с двумя дорожками, выравнивание перетаскиванием клипа и полем сдвига
  (`Alt`+стрелки), явный выбор мастер-трека, layout «рядом / только A / только B».
  Wipe и наложение по решению пользователя не нужны. Известное ограничение: при
  воспроизведении картинка второго окна вывода отстаёт на 0,1–0,2 с при совпадающих
  часах плееров — покадровое сравнение делается на паузе и шаге.
- **Фаза 4 — кэш кадров ffmpeg. Сделана**, см. [docs/phase4-frame-cache.md](docs/phase4-frame-cache.md):
  `CacheBuilder` на ffmpeg CLI (all-intra прокси `-g 1`), `FrameCacheBackend`, автопереключение
  по замеру шага назад (1018 мс → 7 мс на 4K H.264 GOP 250), переиспользование кэша по ключу
  «файл + параметры», настраиваемая частота прокси, лимит 20 ГБ с LRU-очисткой, миниатюры.
  Полоску миниатюр и полосу готовности фаза 2 перенесла на клип таймлайна.
- **Фаза 5 — полировка и упаковка. Сделана**, см. [docs/phase5-polish.md](docs/phase5-polish.md):
  шаттл `J`/`K`/`L` (вперёд — воспроизведением, назад — шагами по таймеру; петля переехала
  на `Ctrl+L`), промотка колесом над кадром (медленно — покадрово, быстро — крупным шагом),
  сессия в JSON (файлы, сдвиг, отрезки, мастер, позиция) с автосохранением и восстановлением
  при запуске плюс сессия отдельным файлом `*.cvp.json`, окно настроек со шпаргалкой по
  клавишам (`F1`), внятные отказы открытия прямо в панели трека, упаковка: `publish.ps1 -Zip`
  и инсталлятор Inno Setup (`tools/installer.iss`, `tools/make-installer.ps1`).
  Общий рендер-таргет для обоих кадров (он снял бы задержку вывода второго окна при
  воспроизведении, см. фазу 3) в фазу не вошёл — это переделка вывода FlyleafHost,
  вынесена отдельной задачей (#16).

Каждая фаза — отдельная задача на доске; заводятся после утверждения плана.

## 6. Риски

- **VFR (переменный fps):** «номер кадра» неоднозначен — работаем по timestamp,
  номер кадра показываем как производный; в кэш-режиме VFR нормализуется прокси.
- **Шаг назад на long-GOP** может быть медленным — закрыто фазами 0 и 4.
- **RAM/VRAM на двух 4K-потоках** — ограничение размера RAM-кэша, аппаратный декод.
- **Дрейф синхронизации при воспроизведении** — периодическая коррекция ведомого; на
  паузе и шаге точность гарантирована точным seek.
- **Дисковый кэш объёмен** (all-intra прокси) — лимит размера кэша + очистка LRU.
