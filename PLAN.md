# ComparisonVideoPlayer — план проекта

Видеоплеер для Windows для покадрового сравнения видео: точный пошаговый просмотр,
синхронное воспроизведение двух роликов и редактируемый таймлайн в стиле видеоредактора.

## 1. Требования (из постановки)

- Windows-приложение.
- Покадровое воспроизведение: шаг вперёд/назад ровно на один кадр, точный seek.
- Если прямой покадровый доступ невозможен/медленный — при открытии строим кэш кадров через ffmpeg.
- Два видео воспроизводятся параллельно и синхронно.
- Вместо стандартной полосы прокрутки — модифицируемый таймлайн (как в видеоредакторах):
  - настройка воспроизводимого отрезка (in/out точки);
  - сопоставление (выравнивание по времени) видео из параллельных треков.

## 2. Исследование технологий

| Вариант | Плюсы | Минусы |
|---|---|---|

| libmpv, встроенный в WPF/Qt | Лучший в классе playback; `frame-step`/`frame-back-step` из коробки | Интеграция через C API/HWND; синхронизировать два инстанса сложнее; UI всё равно свой |
| Electron + WebCodecs | Самый дешёвый в разработке UI таймлайна (HTML/CSS); покадровый декод под полным контролем | Демуксинг свой (mp4box.js и т.п.); ограничения кодеков (HEVC); два параллельных 4K-декода тяжелы; память/упаковка |

над кадрами через FFmpeg, готовый плеерный движок. libmpv — запасной вариант, если
спайк (фаза 0) покажет проблемы с точностью/скоростью шага назад.

## 3. Архитектура

```
+--------------------------------------------------------------+
| WPF UI                                                       |
|  +----------------+  +----------------+                      |
|  | VideoView A    |  | VideoView B    |   (layout: рядом /   |
|  +----------------+  +----------------+    один/два трека)   |
|  +------------------------------------------------------+    |
|  | TimelineControl: линейка, 2 трека, клипы с trim,      |    |
|  | playhead, зум, снэп по кадрам, offset перетаскиванием |    |
|  +------------------------------------------------------+    |
+--------------------------------------------------------------+
| SyncEngine: мастер-клок, транспорт (play/pause/step/speed),  |
| маппинг время-мастера -> локальное время каждого трека       |
+--------------------------------------------------------------+
| PlaybackBackend (интерфейс)                                  |
|   +-- FlyleafBackend: прямой декод, frame step, точный seek  |
|   +-- FrameCacheBackend: кадры из кэша ffmpeg (fallback)     |
+--------------------------------------------------------------+
| CacheBuilder (ffmpeg CLI): фоновая генерация кэша/миниатюр   |
+--------------------------------------------------------------+
```

Ключевые модели: `MediaInfo` (fps, длительность, число кадров, VFR-флаг),
`ClipSegment` (источник, in/out, offset на треке), `SessionProject` (сохранение сессии в JSON).

## 4. Ключевые технические решения

### 4.1 Покадровое воспроизведение — три уровня

1. **Прямой шаг декодером** (основной путь): `ShowFrameNext`/`ShowFramePrev` у Flyleaf.
   Вперёд — тривиально; назад на long-GOP кодеках требует декода от предыдущего
   keyframe — скорость зависит от длины GOP.
2. **RAM-кэш вокруг playhead**: кольцевой буфер уже декодированных кадров
   (например ±N кадров), чтобы шаг назад был мгновенным в рабочей зоне.
3. **Дисковый кэш через ffmpeg (fallback из постановки)**: если формат «тяжёлый»
   (длинный GOP, HEVC/AV1, медленный шаг назад), при открытии в фоне строим
   all-intra прокси (`-g 1`, H.264 или MJPEG) либо извлекаем кадры; после этого любой
   seek/шаг мгновенный. Показ прогресса, кэш переиспользуется между запусками
   (ключ — хэш файла + параметры).

Решение о fallback принимается автоматически по замеру времени шага назад, с ручным
переключением в настройках.

### 4.2 Синхронизация двух видео

- Единый **мастер-клок** в SyncEngine; оба плеера — ведомые: транспортные команды
  (play/pause/step/seek/скорость) идут через движок, никогда напрямую в плеер.
- Позиция трека = `master_time - track_offset`, обрезанная по in/out клипа.
- Разные fps у треков: шаг задаётся кадрами мастер-трека (выбираемого), ведомый
  сопоставляется по времени (ближайший кадр).
- Контроль рассинхрона: при воспроизведении периодическая коррекция ведомого,
  при паузе/шаге — точный seek обоих.

### 4.3 Таймлайн (кастомный WPF-контрол)

- Линейка времени с зумом (колесо) и панорамированием, снэп к границам кадров.
- 2 трека; на каждом клип с ручками trim (in/out — воспроизводимый отрезок).
- Перетаскивание клипа по треку = offset (сопоставление видео между треками).
- Playhead с прокруткой (scrub) — покадровая точность.
- Опционально: полоска миниатюр на клипе (ffmpeg-генерация в фоне), маркеры.

## 5. Этапы работ

- **Фаза 0 — спайк (валидация стека).** Мини-приложение на Flyleaf: открыть 4K
  H.264/HEVC long-GOP, замерить шаг вперёд/назад, два плеера одновременно.
  Критерий: шаг назад ≤ ~200 мс, иначе — приоритет фазе 4 (кэш) или переход на libmpv.
- **Фаза 1 — MVP одиночного плеера.** Открытие файла (диалог + drag&drop),
  play/pause, шаг ±1 кадр, таймкод и номер кадра, простая шкала позиции.
- **Фаза 2 — таймлайн.** Контрол с зумом/снэпом, playhead со скрабом, trim-ручки
  отрезка воспроизведения, петля по отрезку.
- **Фаза 3 — второй трек и синхронизация.** SyncEngine, offset перетаскиванием,
  синхронный транспорт, layout сравнения (рядом; далее — wipe/overlay).
- **Фаза 4 — кэш кадров ffmpeg.** CacheBuilder, автопереключение на fallback,
  переиспользование кэша, миниатюры на клипах.
- **Фаза 5 — полировка.** Горячие клавиши (←/→ шаг, JKL, Space), сохранение
  сессии (файлы, offset, in/out), настройки, упаковка (single-file publish / инсталлятор).

Каждая фаза — отдельная задача на доске; заводятся после утверждения плана.

## 6. Риски

- **VFR (переменный fps):** «номер кадра» неоднозначен — работаем по timestamp,
  номер кадра показываем как производный; в кэш-режиме VFR нормализуется прокси.
- **Шаг назад на long-GOP** может быть медленным — закрыто фазами 0 и 4.
- **RAM/VRAM на двух 4K-потоках** — ограничение размера RAM-кэша, аппаратный декод.
- **Дрейф синхронизации при воспроизведении** — периодическая коррекция ведомого; на
  паузе и шаге точность гарантирована точным seek.
- **Дисковый кэш объёмен** (all-intra прокси) — лимит размера кэша + очистка LRU.
